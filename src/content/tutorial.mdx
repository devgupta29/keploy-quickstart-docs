## What We Are Building

In standard backend development, writing end-to-end and regression tests is slow and brittle:
1. You have to craft mock data structures by hand.
2. You write boilerplate HTTP client assertions for every response code and payload key.
3. Upstream API dependencies must be stubbed with mock servers.
4. Test suites rot over time as APIs evolve.

**Keploy flips this paradigm.** Instead of writing tests, you **record real API interactions** as your application runs. Keploy captures incoming HTTP requests, intercepts outgoing HTTP dependencies (like upstream REST APIs), and records both as deterministic YAML test cases. When you replay tests, Keploy stubs downstream calls with the recorded data and verifies that your application produces the exact expected responses.

In this quickstart, we will:
* Set up the official **`samples-go/http-pokeapi`** application (a Go HTTP service built with the Chi router that queries the public PokéAPI).
* Run Keploy in **RECORD mode** to capture live traffic to `/api/greet`, `/api/pokemon/pikachu`, and `/api/locations`.
* Inspect the auto-generated YAML test cases in `keploy/test-set-1/tests`.
* Run Keploy in **TEST mode** to replay traffic and achieve a green test suite (**8 passed, 0 failed, 10.29s**) with **zero manual test code**.

## Step 5: Record API Traffic with Keploy

### RECORD Mode vs. TEST Mode: What is the difference?
* **RECORD mode (`keploy record`)**: Keploy launches your application as a child process. It attaches network interception hooks. When client requests arrive, Keploy forwards them to your Go handlers, observes the responses, and saves the HTTP request/response pair to YAML files on disk. If your app calls an external API, Keploy captures that downstream call as a reusable mock.
* **TEST mode (`keploy test`)**: Keploy boots your application cleanly, reads the YAML test cases from disk, re-sends each recorded request, intercepts any external API calls with the recorded mocks, and computes an automated assertion diff against the recorded response.

<Steps>
  <Step number={1} title="Launch the app in RECORD mode">
    In your project root (`~/samples-go/http-pokeapi`), start Keploy in record mode:
    <CodeBlock language="bash" isCommand={true} code={recordCmd} />

    **Why `-c "./main"`?**
    The `-c` (command) flag instructs Keploy to manage the lifecycle of your binary. Keploy initializes its proxy engine first, launches `./main`, and monitors socket file descriptors for incoming requests on port 8080.
  </Step>

  <Step number={2} title="Drive real HTTP traffic to record test cases">

<CodeBlock language="yaml" filename="keploy/test-set-1/tests/get-api-greet-1.yaml" code={testYamlSample} />

### Key Elements of a Keploy Test Case:
1. **`req`**: Stores the exact HTTP method (`GET`), URL path (`/api/greet`), headers, and request body.
2. **`resp`**: Stores the exact expected status code (`200 OK`), headers (`Content-Type: text/plain`), and response payload.
3. **`assertions.noise`**: Fields like `header.Date` or timestamps that change on every execution are automatically tagged as noise. Keploy ignores noise fields during comparison so tests never fail due to dynamic dates or random IDs!

## What Happened Under the Hood?

Understanding Keploy's architecture makes debugging and CI maintenance straightforward:

<DiagramBox title="Keploy Architecture: Record vs. Replay">
  ```
  === 1. RECORD PHASE ===
  [curl / Client]
         │
         ▼  (HTTP GET :8080)
  ┌──────────────┐
  │ Keploy Proxy │ ─── Attaches eBPF probe / socket hook
  └──────┬───────┘
         │ Passes request to app
         ▼
  ┌──────────────┐
  │  ./main (Go) │ ─── Makes upstream HTTP call ───► [pokeapi.co]
  └──────┬───────┘                                         │
         │                                                 ▼
         │ ◄── Returns response & captures mock ───────────┘
         ▼
  [Write to Disk: keploy/test-set-1/tests/*.yaml]


  === 2. REPLAY (TEST) PHASE ===
  ┌──────────────────┐
  │   Keploy Test    │
  │     Runner       │
  └────────┬─────────┘
           │ 1. Sends recorded request from YAML
           ▼
  ┌──────────────────┐
  │  ./main App (Go) │
  └────────┬─────────┘
           │ 2. App attempts outbound call to pokeapi.co
           ▼
  ┌──────────────────┐
  │ Keploy Mock Trap │ ─── Intercepts call; returns saved mock (No internet needed!)
  └────────┬─────────┘
           │ 3. App returns response to Keploy Test Runner
           ▼
  ┌──────────────────┐
  │ Assertion Engine │ ─── Diff actual vs. expected YAML (Ignoring noise)
  └────────┬─────────┘
           ▼
       [PASSED ✓]
  ```
</DiagramBox>

## Troubleshooting Common Issues

<Callout type="danger" title="Issue: Port 8080 already in use">
  <strong>Symptom:</strong> Keploy or your Go application logs: <code>bind: address already in use</code>.<br />
  <strong>Fix:</strong> An orphaned server instance is still occupying port 8080. Kill it using:<br />
  <code>sudo fuser -k 8080/tcp</code><br />
  or find the PID and terminate it with: <code>lsof -i :8080</code> then <code>kill -9 &lt;PID&gt;</code>.
</Callout>

<Callout type="warning" title="Issue: Wrong command path in keploy test (-c)">
  <strong>Symptom:</strong> Keploy outputs <code>exec: "./main": stat ./main: no such file or directory</code>.<br />
  <strong>Fix:</strong> Ensure you are in the directory containing your compiled binary (<code>~/samples-go/http-pokeapi</code>) and that you built the binary with <code>go build -o main</code> prior to running Keploy.
</Callout>

<Callout type="note" title="Issue: API server URL notices or license warnings">
  <strong>Symptom:</strong> Keploy logs <code>INFO Starting Keploy &#123;&quot;apiServerURL&quot;: &quot;https://api.keploy.io&quot;&#125;</code>.<br />
  <strong>Explanation:</strong> This is normal informational telemetry for Keploy Free Edition. No paid API key or enterprise registration is required to record or replay tests locally.
</Callout>

## What to Commit to Git

When adding Keploy to your team's workflow, version control your test suite alongside your source code:

### Files to Commit:
* `keploy/` directory (all `test-set-*/tests/*.yaml` files and mocks).
* `keploy.yml` (Keploy configuration file specifying ignored paths and noise rules).
* `go.mod` and `go.sum`.

### Files to Ignore in `.gitignore`:
* Compiled binaries (`main`, `*.exe`).
* Temporary debug logs (`keploy-logs.txt`).
